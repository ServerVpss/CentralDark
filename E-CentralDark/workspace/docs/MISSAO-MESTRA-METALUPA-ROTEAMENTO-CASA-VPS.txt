- tarefas remotas retornam BLOCKED ou usam fallback autorizado;
- nenhuma chave da VPS é copiada para Casa;
- nenhuma ação perigosa é rebaixada para fallback textual.

CONFIGURAÇÃO CANÔNICA

Primeiro localizar arquivos equivalentes.

Somente se não houver equivalente, propor:
- schema canônico;
- configuração-base;
- overlay Casa;
- overlay VPS;
- registry de capacidades;
- versão/hash da política.

Não criar arquivos paralelos se rotas.json suportar extensão segura.

HOT-RELOAD

Somente habilitar se o runtime provar suporte.

Exigir:
- schema validation;
- version/hash;
- reload atômico;
- rollback;
- último config válido;
- evento de auditoria.


======================================================================
GATE C2 — DUELO DE ARQUITETURAS, SOMENTE SE RESTAR DÚVIDA REAL
======================================================================

Não criar duas branches por diversão.

Só executar duelo se o inventário deixar duas soluções plausíveis e incompatíveis.

A — VPS-CENTRIC:
Casa encaminha quase tudo para o Elite Gateway.

B — HÍBRIDA:
Casa classifica e resolve localmente quando permitido;
VPS resolve provider, custo, escala e continuidade.

REGRAS

- mesma base origin/main;
- mesmas fixtures;
- mesmos testes imutáveis;
- sem produção;
- sem secrets;
- branches experimentais;
- medir latência, custo, disponibilidade, tokens, privacidade, qualidade,
  fallback, recuperação, complexidade e regressão.

A vencedora vira candidata canônica.
A perdedora não permanece como sistema paralelo.

Se a evidência já mostrar que B domina A:
não criar duelo artificial.


======================================================================
GATE D — IMPLEMENTAÇÃO E GIT
======================================================================

Não misturar reconciliação da Lupa e roteamento num mega-PR.

Usar UM arquivo de missão, com PRs separados e ligados:

PR-A — LUPA CANÔNICA
- somente reconciliação da skill;
- profile/link;
- testes;
- documentação necessária;
- base origin/main.

PR-B — ROTEAMENTO HÍBRIDO
- stacked PR sobre a branch do PR-A, OU
- PR posterior a origin/main depois do PR-A;
- DEPENDS_ON=PR-A;
- sem merge automático.

BRANCHES SUGERIDAS

PR-A:
reconcile/lupa-unica-<timestamp>

PR-B:
feat/roteamento-hibrido-casa-vps-<timestamp>

IMPLEMENTAÇÃO MÍNIMA DO PR-B

1. Documento consolidado.
2. Inventário do existente.
3. ADR comparando os planos.
4. Registry real de modelos/capacidades.
5. Extensão mínima do roteador existente.
6. Fallback com orçamento, circuit breaker, backoff, capability gate,
   privacy gate e fail-closed para ação.
7. Auditoria/ledger.
8. Configuração Casa.
9. Configuração VPS.
10. Testes determinísticos.
11. Exemplos reproduzíveis.
12. Nenhum deploy.

Antes de tocar áreas protegidas, provar necessidade, menor diff, rollback e testes.

Se exigir deploy ou migration real:
implementar arquivo e teste no PR;
marcar ACTIVATE_LATER=SIM;
não executar.
