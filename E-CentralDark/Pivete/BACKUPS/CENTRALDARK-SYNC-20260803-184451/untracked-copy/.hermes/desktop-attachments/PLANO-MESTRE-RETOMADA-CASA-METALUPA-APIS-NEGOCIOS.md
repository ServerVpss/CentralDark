# 0. A VERDADE QUE MUDA O RUMO

O travamento não aconteceu porque o Pivete não sabia o que queria.

O travamento aconteceu porque as IAs entregavam:

```text
documentos
→ comandos
→ código
→ gates repetidos
→ novas camadas
→ mais decisões manuais
```

quando o Pivete queria:

```text
FALAR O QUE QUER
→ VER A CONSTRUÇÃO AO VIVO
→ AJUSTAR VISUALMENTE
→ APROVAR
→ PUBLICAR
→ VOLTAR SE PRECISAR
```

O objetivo não é transformar o Pivete em operador de terminal.

O objetivo é construir uma **fábrica visual autônoma de sites, módulos e negócios**, governada pelo Pivete, executada pelos agentes e observável em tempo real.

# 1. DECISÃO ARQUITETURAL CENTRAL

## Um Jarvis, dois corpos de execução, uma autoridade

Não criar duas personalidades concorrentes nem duas memórias pessoais.

```text
UMA IDENTIDADE OPERACIONAL
→ SOL / JARVIS DO PIVETE

UMA AUTORIDADE FINAL
→ PIVETE

UMA MEMÓRIA LÓGICA CANÔNICA
→ ACESSADA PELA API CENTRAL
→ PERSISTÊNCIA SEMÂNTICA NA MELHOR CAMADA PROVADA
→ CASA E VPS RECEBEM SOMENTE O CONTEXTO NECESSÁRIO

DOIS CORPOS DE EXECUÇÃO
→ HERMES-CASA
→ WORKER/HERMES-VPS
```

### Corpo 1 — Hermes da Casa

É o corpo residencial e interativo:

```text
olhos
→ telas, navegadores, janelas e estado visual autorizados

ouvidos
→ microfone, Telegram, voz e eventos autorizados

boca
→ áudio, texto, notificações e respostas

braços
→ mouse, teclado, navegador, arquivos e ferramentas locais

pernas
→ navegação entre Casa, GitHub, Builder e VPS

memória da SOL
→ acessada pela API
→ sessão local com cache mínimo quando necessário
→ persistência central semântica e auditável
```

É onde a SOL é utilizada de forma residencial e interativa. A fonte persistente da memória não precisa morar fisicamente no PC.

A Casa acessa, conforme autorização:

- contexto necessário;
- rotina;
- preferências;
- memória semântica e operacional;
- interação por voz;
- controle dos monitores;
- assistência cotidiana;
- proteção da Casa;
- tradução do mundo técnico para o Pivete.

### Corpo 2 — Worker/Hermes da VPS

É o braço empresarial permanente:

- mantém Builder/Bolt e previews disponíveis;
- cria workspaces isolados;
- executa builds e testes;
- opera deploy e rollback;
- coleta logs e métricas;
- atende tarefas assinadas pelo Hermes da Casa ou pelo Portal;
- não carrega a memória pessoal completa;
- não assume a identidade do Pivete;
- não toma decisão final;
- não vira um segundo Jarvis concorrente.

### Fórmula

```text
UM SOUL
+ UMA MEMÓRIA LÓGICA ACESSÍVEL PELA API
+ HERMES COMO EXECUTOR
+ MODELOS INTERCAMBIÁVEIS
+ UMA FONTE DE VERDADE
= CONTINUIDADE SEM DUPLICAÇÃO
```

# 4. O PRODUTO QUE O PIVETE REALMENTE QUER

## Fluxo principal

```text

2. Fala ou escreve o que quer.
3. SOL transforma a intenção em tarefa.
```

# 5. INVENTÁRIO HONESTO — LOVABLE

## O que foi observado como valioso

O Lovable demonstra um padrão de experiência útil:

- conversa orientada ao projeto;
- plano visível antes da mudança;
- edição ligada ao projeto;
- preview rápido;
- comparação visual;
- fluxo de aprovação;
- publicação simplificada;
- integração entre IA e interface;
- redução do contato direto com código.

## O que não deve ser copiado como dependência

- dependência de créditos;
- dependência de uma interface de terceiro;
- bloqueio do fluxo quando pagamento ou serviço falha;
- conhecimento preso na conversa;
- código ou arquitetura proprietária não autorizada;
- criação de outra fonte de verdade;
- planos que ignoram o runtime real já existente.

## O que deve ser absorvido

```text
PADRÃO DE INTERAÇÃO
→ sim

EXPERIÊNCIA VISUAL
→ sim

LOOP IA → PREVIEW → AJUSTE
→ sim

PUBLICAÇÃO SIMPLES
→ sim

DEPENDÊNCIA DO LOVABLE
→ não

CÓPIA CEGA DE CÓDIGO
→ não
```

O Lovable é referência de experiência, não destino obrigatório.

# 8. PONTE CASA ↔ VPS

A ponte não deve depender de copiar tokens manualmente nem expor a Casa diretamente.

## Contrato mínimo

```text
TASK_ID
ORIGIN
OWNER
MISSION
SCOPE
PROJECT
ALLOWED_ACTIONS
DENIED_ACTIONS
INPUTS
EXPECTED_OUTPUT
TIMEOUT
ROLLBACK
EVIDENCE_REQUIRED
AUTHORIZATION_ID
```

## Fluxo

```text
Hermes-Casa cria contrato
→ assina/autentica
→ Worker-VPS recebe
→ executa no workspace permitido
→ transmite eventos
→ devolve resultado + evidência
→ Hermes-Casa traduz
→ Pivete decide
```

## O que atravessa a ponte

- tarefa;
- escopo;
- estado necessário;
- eventos;
- evidência;
- artefatos;
- resultado;
- hashes e referências sanitizadas.

## O que não atravessa por padrão

- memória pessoal completa;
- histórico íntimo desnecessário;
- tokens em texto;
- cookies;
- segredo bruto;
- acesso ilimitado ao PC;
- autoridade final.

# 10. MEMÓRIA — LEVEZA PARA A CABEÇA DO PIVETE

## Uma memória lógica canônica, acessível em qualquer canal

```text
HOJE
→ missão atual, pendência, evidência e próximo passo

SEMANA
→ continuidade, padrões, decisões em maturação

REGRAS
→ conhecimento estável, testado e aprovado
```

## Separação necessária

```text
MEMÓRIA DA SOL
→ uma camada lógica central
→ acessada por sessão, identidade, missão e autorização
→ persistência preferencial em Postgres/Supabase + busca semântica, se provado adequado
→ o Desktop pode manter cache operacional; não precisa ser a fonte definitiva

MEMÓRIA OPERACIONAL DA VPS
→ tarefas, builds, previews, deploys, incidentes, projetos e evidências
→ separada por escopo e projeto
→ não recebe contexto pessoal desnecessário
```

## Recuperação

Quando uma sessão perder o fio:

```text
LER PLANO
→ LER HOJE
→ LER SEMANA
→ LER ESTADO DO PROJETO
→ LER LOGS
→ RECONSTRUIR
→ DECLARAR O QUE FOI RECUPERADO
```

Sessão nova não significa começar do zero.

# 11. SEGURANÇA SEM BUROCRACIA

O Pivete não deve ser obrigado a confirmar vinte vezes.

## Autorização por missão

```text
PIVETE AUTORIZA O ESCOPO UMA VEZ
→ sistema trabalha dentro do contrato
→ só interrompe por bloqueio real
```

## Proteções invisíveis no motor

- workspace isolado;
- backup automático;
- diff;
- teste;
- snapshot;
- segredo fora de logs;
- limite por projeto;
- publicação explícita;
- rollback pronto;
- proteção contra force-push;
- proteção contra exclusão fora do escopo;
- proteção contra produção errada;
- registro automático.

## Quando interromper o Pivete

Somente quando houver:

- escolha de produto;
- risco real de perda;
- gasto novo;
- publicação;
- conflito de intenção;
- ausência de credencial indispensável;
- alvo não identificável;
- resultado visual que exige gosto pessoal.

Todo o restante deve ser pesquisado e resolvido pelos agentes.

# 13. BUILDER — COMPONENTES OBRIGATÓRIOS

## 13.1 Projetos

- criar a partir de template;
- importar repositório;
- importar módulo existente;
- clonar projeto;
- arquivar;
- restaurar;
- mostrar origem e proprietário.

## 13.2 Workspace isolado

- um workspace por projeto/execução;
- branch ou snapshot identificável;
- dependências isoladas;
- limite de recursos;
- limpeza controlada;
- persistência dos artefatos aprovados.

## 13.3 Chat de construção

- conversa com contexto do projeto;
- escolha automática de modelo;
- ordens em linguagem comum;
- plano breve;
- execução;
- progresso visível;
- explicação do resultado.

## 13.4 Preview ao vivo

- URL própria por workspace;
- HMR quando aplicável;
- estado carregando/pronto/falhou;
- captura automática;
- comparação visual;
- console coletado;
- erro traduzido.

A tecnologia final — WebContainer, container remoto, iframe ou combinação — só será decidida depois do inventário real.

## 13.5 Loop automático

```text
ALTERAÇÃO
→ BUILD
→ PREVIEW
→ ERRO?
   → classificar
   → corrigir
   → testar novamente
→ RESULTADO VISUAL
```

Abortar quando houver estagnação real, não por limite arbitrário.

## 13.6 Publicação

O botão PUBLICAR deve:

1. congelar o candidato;
2. registrar referência;
3. executar testes definidos;
4. mostrar impacto;
5. criar commit/PR ou promoção configurada;
6. publicar;
7. verificar saúde;
8. guardar rollback;
9. informar resultado em linguagem simples.

## 13.7 Voltar

- listar versões;
- mostrar miniatura/diferença;
- restaurar candidato anterior;
- verificar saúde;
- preservar histórico.

# 24. SUPABASE COMO PLANO DE ESTADO E CONTROLE

Supabase pode reduzir muito o peso da arquitetura, desde que não seja confundido com o executor pesado.

Usos recomendados, após inventário do que já existe:

```text
AUTH
→ identidade do Pivete, dispositivos e sessões

POSTGRES
→ projetos, tarefas, estados, contratos e auditoria

PGVECTOR
→ memória semântica e recuperação de contexto

REALTIME / BROADCAST
→ eventos ao vivo do Builder, Worker e painéis

QUEUES / PGMQ
→ fila durável de missões e trabalhos

CRON
→ manutenção, verificações e rotinas agendadas

STORAGE
→ ZIPs, screenshots, artefatos, candidatos e relatórios

VAULT / SECRETS
→ referências de credenciais sem expor valor no chat

EDGE FUNCTIONS
→ endpoints curtos, autenticação, webhooks e roteamento leve
```

O que NÃO deve ser empurrado para Edge Functions:

- builds longos;
- instalação pesada;
- containers por projeto;
- testes demorados;
- browser/desktop automation;
- loops agentivos permanentes;
- processamento que precisa sobreviver por horas.

Esses trabalhos ficam em workers/containers na VPS.

Fórmula:

```text
SUPABASE
→ estado, memória, fila, eventos e controle

VPS
→ execução pesada e permanente

HERMES
→ decisão operacional e ferramentas

BOLT
→ experiência visual
```

# 25. REACT COMO MÉTODO, NÃO COMO NOVO CÉREBRO

ReAct combina observação, raciocínio orientado à tarefa e ação com ferramentas.

Aplicação prática na CentralDark:

```text
OBSERVAR
→ estado real, tela, arquivo, log ou resposta

DECIDIR
→ próximo passo justificável

AGIR
→ ferramenta autorizada

OBSERVAR RESULTADO
→ confirmar ou corrigir

REPETIR
→ até critério visual e operacional
```

Correções do Pivete devem alimentar uma trilha estruturada:

```text
MISSÃO
OBSERVAÇÃO
AÇÃO
RESULTADO
CORREÇÃO_DO_PIVETE
REGRA_APRENDIDA
TESTE_DE_REGRESSÃO
```

Não depender de expor pensamento privado do modelo.

Registrar decisões, ações, evidências e resumos de justificativa suficientes para auditoria.

Fine-tuning de modelo menor é etapa futura, somente depois de existir conjunto limpo de trajetórias corrigidas e teste que prove ganho. O resultado de pesquisa em outros benchmarks não garante ganho automático na CentralDark.

# 26. ESCOLHA DE FRAMEWORK — NÃO INSTALAR TODOS

O núcleo atual continua:

```text
HERMES
+ GATEWAY/ROUTER CENTRALDARK
+ BOLT EXISTENTE
+ SUPABASE
+ WORKERS DA VPS
```

Frameworks externos entram apenas como peças, depois de provar uma lacuna.

## Vercel AI SDK

Candidato para:

- streaming do chat no Builder;
- tool calls;
- troca de modelo;
- eventos do agente na interface;
- frontend TypeScript.

Não é o executor completo da VPS.

## Mastra

Candidato principal para um piloto TypeScript, caso o Bolt precise de:

- workflows;
- agentes;
- memória;
- MCP;
- observabilidade;
- OpenAPI;
- execução self-hosted.

Não substituir Hermes nesta fase.

Primeiro testar como motor interno de uma função isolada do Builder.

## LangGraph

Reserva para fluxo crítico que exija:

- checkpoints;
- retomada após falha;
- estado explícito;
- time travel;
- human-in-the-loop complexo.

Só adotar se a necessidade compensar criar uma camada Python/graph adicional.

## PydanticAI

Útil para microagentes Python com:

- entradas e saídas tipadas;
- validação rigorosa;
- limites de uso;
- integração com MCP;
- execução durável por ferramenta externa.

Não é a fábrica visual completa.

## CrewAI

Pode servir em comitês limitados de pesquisa.

Não usar como núcleo agora, porque múltiplos papéis autônomos podem aumentar custo, repetição e dificuldade de depuração.

## LangChain

Não é prioridade. O Hermes já oferece agente, ferramentas e skills. Adicionar outra camada geral antes de provar uma lacuna recriaria o travamento.
