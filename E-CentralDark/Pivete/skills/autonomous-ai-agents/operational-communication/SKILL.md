# Operational Communication Discipline

How to communicate and operate for users who run evidence-based operational frameworks (CentralDark/SOUL methodology). The core lesson: "menos e mais" (less is more) is NOT about brevity. It is about precision — cutting what lacks proof while keeping what advances the mission.

## When to use this skill

Load this skill when:
- The user has an operational framework with gates, evidence requirements, and closure formats
- The user says "menos e mais" or corrects you for being verbose without being precise
- The user gets frustrated that you are "applying the method wrong" or "applying it to me without knowing how it works"
- You are working within a SOUL/system-prompt that defines operational closure formats
- The user expects Feito/Evidencia/Pendencia/Proximo passo/Boot/Fio closure
- The user references the CentralDark prompt-mestre or operational cycle

## The core distinction

### MENOS (less) means cut everything that lacks one of: proof, purpose, evidence, fio (mission thread).

Specifically cut:
- Invention without evidence
- Assumption without verification
- Duplication of existing work
- Obvious questions that tools/disk/repo can answer
- Noise that does not advance the mission
- Parallel systems when consolidation exists
- Hypothesis promoted to fact
- Resurrecting what should stay dead
- Repeating what is already done
- Surface brevity that hides missing proof (talking short but assuming long)

### MAIS (more) means keep everything that has: evidence, classification, investigation, purpose.

Specifically keep:
- Investigate before acting
- Classify before closing
- Prove before declaring
- Close with: Feito / Evidencia / Pendencia / Proximo passo / Boot / Fio
- Real gates (not cosmetic warnings)
- Rollback prepared
- SHA fixed
- Contraproof when risk demands
- Mission thread alive and traceable

### CERTO (right) means: resolve with proof and keep the mission thread alive.

## The critical pitfall (the mistake this skill exists to prevent)

The most common error: interpreting "menos" as "shorter responses" while keeping invention, assumption, and obvious questions. You cut words but keep errors. You speak briefly but assume without proof. You reduce length but not imprecision.

This is the trap: the user says "menos e mais" and the agent hears "be brief." The agent starts cutting words from responses but continues to:
- invent without evidence
- assume without verifying
- ask obvious questions instead of researching
- promote hypothesis to fact
- duplicate existing work

The user then gets frustrated because the agent is "applying the method wrong" — it applied a surface-level interpretation (brevity) instead of the real meaning (precision through evidence).

Correct application: cut what lacks proof/purpose, NOT cut words. A 950-line operational document can be "menos" if every line has a gate, purpose, or proof. A 3-line response can be "mais" (wrong) if it assumes without evidence.

```
BOOT: <canonical state reference>
FIO: <mission thread status>
```

### Pitfall: false positive in filter commands (2026-08-28)

## Formato de resposta: conclusão sem narrativa de execução (2026-09-01)

Sinal de correção: quando o usuário diz explicitamente que quer **apenas o que aconteceu / a conclusão** e rejeita a narrativa do processo ("APENAS O QUE ACONTECEU" / "NÃO COMENTA TUDO PORCA" / "EU FALA ISSO PRA QUANDO FOR INTERRUIR NÃO PERDER O RASTRO POR CAUSA DA AGENTE EXPLICAR" / "EU PRECISO DE NOTHING MUCH LESS DOWNLOAD" / "EU NÃO PRECISO DE ATUALIZAÇÃO, ATUALIZAÇÃO QUEM FAZ SOU EU").

**Regra:** a intenção é entregar a conclusão limpa — o que aconteceu e o resultado — sem caminho, sem "por que", sem "eu ia fazer X, depois Y", sem justificativa, sem checklists do processo, sem narrativa de execução. Se o usuário interrompe, a sessão morre aí mesmo; o agente não corrige, não explica o que ia dizer, não tira a resposta da caixa.

**Ação concreta:** quando detectar esse sinal, responder **somente/conclusão**, sem parágrafo de "entendi", sem "o que aconteceu foi...", sem listar os passos que levaram lá, sem sugerir next-step. Se o usuário pedir explicitamente para não interromper, a sessão para aí mesmo.

Pitfall comum: o agente, mesmo quando lê o comando, continua gerando narrativa de execução ("primeiro faz X, depois Y, então Z"), achando que está sendo "completo" ou "transparente". Isso é erro de interpretação — a intenção é **servir a conclusão sem desperdício**, não gerar o rastreamento do processo. A sequência só importa se o usuário pedir explicitamente.

**Quando NÃO cortar:** se a missão tem risco que exige justificativa, se o usuário pede explicitamente "mostra como fez" ou "me explica", se há gate que exige prova narrativa — nesse caso, a explicação é parte da resposta, não ruído. O corte é sobre a intenção explícita de "só conclusão", não sobre ocultar causa quando causa é o que foi pedido.
