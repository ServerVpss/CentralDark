# 2026-10-04 — Binding definitivo SOL ↔ HERMES; Pivete deixa de ser papel técnico

## Decisão do CHEFE

A arquitetura operacional passa a ter somente os papéis necessários:

```text
SEGREDO/CHEFE = humano + intenção + autoridade final
SOL = coordenação cognitiva oficial
HERMES = executor + preservação + continuidade
MODELO = motor substituível
VOICE|TEXT|CHAT|AION|DESKTOP = superfícies da SOL
PIVETE = vocativo/histórico somente
```

Não nasce novo agente. O Hermes original é suficiente como executor quando possui as capabilities aplicáveis à missão.

## Ferida corrigida

O termo `PIVETE/HERMES` havia se tornado um binding técnico misturado. Isso podia induzir loaders/engines a tratar um vocativo histórico como identidade operacional.

Também havia outra ambiguidade: entregar `SOUL-SOL` integralmente ao Hermes poderia ser interpretado como promoção do Hermes para função SOL se o role binding não fosse resolvido antes.

Correção:

```text
LOAD_SOUL
→ RESOLVE_ROLE
→ ROLE=SOL     => coordenar
→ ROLE=HERMES  => executar
```

Hermes pode consumir a SOUL, memória, owners, intenção e regras da Casa; não assume `IDENTIDADE=SOL_JARVIS...`.

## Auto-repair de drift

```text
ROLE_DRIFT_AUTO_REPAIR=true
CURRENT_PIVETE_TECHNICAL_ROLE → HERMES
PIVETE_HISTORICAL_PROVENANCE → PRESERVE_AS_HISTORY
PIVETE_VOCATIVE → ALLOWED_NO_TECHNICAL_MEANING
NO_REASK_FOR_ALREADY_AUTHORIZED_ROLE_NORMALIZATION=true
```

A correção automática vale para consumidores CURRENT/operacionais. Histórico não é apagado nem reescrito como se nunca tivesse existido.

## Operação prática atual

Enquanto a superfície SOL não tiver shell/bridge vivo:

```text
CHEFE
→ SOL consulta Docs/CURRENT
→ SOL gera missão/comando
→ CHEFE entrega ao terminal/painel
→ HERMES com shell executa
→ Hermes mede/prova/contraprova
→ estado volta para SOL
```

Quando Zendrive/Desktop/MCP ou outra ponte provar shell vivo, SOL pode orquestrar Hermes por essa rota sem mudança de identidade.
