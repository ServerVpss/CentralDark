# 0. A VERDADE QUE MUDA O RUMO

O travamento não aconteceu porque o Pivete não sabia o que queria.

O travamento aconteceu porque as IAs entregavam:

```text
documentos
→ comandos
→ código
→ gates repetidos
→ novas camadas
→ mais decisões manuais
```

quando o Pivete queria:

```text
FALAR O QUE QUER
→ VER A CONSTRUÇÃO AO VIVO
→ AJUSTAR VISUALMENTE
→ APROVAR
→ PUBLICAR
→ VOLTAR SE PRECISAR
```

O objetivo não é transformar o Pivete em operador de terminal.

O objetivo é construir uma **fábrica visual autônoma de sites, módulos e negócios**, governada pelo Pivete, executada pelos agentes e observável em tempo real.

# 1. DECISÃO ARQUITETURAL CENTRAL

## Um Jarvis, dois corpos de execução, uma autoridade

Não criar duas personalidades concorrentes nem duas memórias pessoais.

```text
UMA IDENTIDADE OPERACIONAL
→ SOL / JARVIS DO PIVETE

UMA AUTORIDADE FINAL
→ PIVETE

UMA MEMÓRIA PESSOAL CANÔNICA
→ CASA

DOIS CORPOS DE EXECUÇÃO
→ HERMES-CASA
→ WORKER/HERMES-VPS
```

### Corpo 1 — Hermes da Casa

É o corpo residencial e interativo:

```text
olhos
→ telas, navegadores, janelas e estado visual autorizados

ouvidos
→ microfone, Telegram, voz e eventos autorizados

boca
→ áudio, texto, notificações e respostas

braços
→ mouse, teclado, navegador, arquivos e ferramentas locais

pernas
→ navegação entre Casa, GitHub, Builder e VPS

memória pessoal
→ HOJE, SEMANA e REGRAS
```

É onde ficam:

- contexto pessoal;
- rotina;
- preferências;
- memória das 3 Temperaturas;
- interação por voz;
- controle dos monitores;
- assistência cotidiana;
- proteção da Casa;
- tradução do mundo técnico para o Pivete.

### Corpo 2 — Worker/Hermes da VPS

É o braço empresarial permanente:

- mantém Builder/Bolt e previews disponíveis;
- cria workspaces isolados;
- executa builds e testes;
- opera deploy e rollback;
- coleta logs e métricas;
- atende tarefas assinadas pelo Hermes da Casa ou pelo Portal;
- não carrega a memória pessoal completa;
- não assume a identidade do Pivete;
- não toma decisão final;
- não vira um segundo Jarvis concorrente.

### Fórmula

```text
UM SOUL
+ UMA MEMÓRIA PESSOAL
+ DOIS CORPOS
+ UMA FONTE DE VERDADE
= CONTINUIDADE SEM DUPLICAÇÃO
```

# 4. O PRODUTO QUE O PIVETE REALMENTE QUER

## Fluxo principal

```text
1. Pivete abre o HUB ou Builder.
2. Fala ou escreve o que quer.
3. SOL transforma a intenção em tarefa.

8. Pivete vê o resultado.

PUBLICAR
VOLTAR

```

O código existe, mas não ocupa o centro da experiência.

# 5. INVENTÁRIO HONESTO — LOVABLE

## O que foi observado como valioso

O Lovable demonstra um padrão de experiência útil:

- conversa orientada ao projeto;
- plano visível antes da mudança;
- edição ligada ao projeto;
- preview rápido;
- comparação visual;
- fluxo de aprovação;
- publicação simplificada;
- integração entre IA e interface;
- redução do contato direto com código.

## O que não deve ser copiado como dependência

- dependência de créditos;
- dependência de uma interface de terceiro;
- bloqueio do fluxo quando pagamento ou serviço falha;
- conhecimento preso na conversa;
- código ou arquitetura proprietária não autorizada;
- criação de outra fonte de verdade;
- planos que ignoram o runtime real já existente.

## O que deve ser absorvido

```text
PADRÃO DE INTERAÇÃO
→ sim

EXPERIÊNCIA VISUAL
→ sim

LOOP IA → PREVIEW → AJUSTE
→ sim

PUBLICAÇÃO SIMPLES
→ sim

DEPENDÊNCIA DO LOVABLE
→ não

CÓPIA CEGA DE CÓDIGO
→ não
```

O Lovable é referência de experiência, não destino obrigatório.

# 8. PONTE CASA ↔ VPS

A ponte não deve depender de copiar tokens manualmente nem expor a Casa diretamente.

## Contrato mínimo

```text
TASK_ID
ORIGIN
OWNER
MISSION
SCOPE
PROJECT
ALLOWED_ACTIONS
DENIED_ACTIONS
INPUTS
EXPECTED_OUTPUT
TIMEOUT
ROLLBACK
EVIDENCE_REQUIRED
AUTHORIZATION_ID
```

## Fluxo

```text
Hermes-Casa cria contrato
→ assina/autentica
→ Worker-VPS recebe
→ executa no workspace permitido
→ transmite eventos
→ devolve resultado + evidência
→ Hermes-Casa traduz
→ Pivete decide
```

## O que atravessa a ponte

- tarefa;
- escopo;
- estado necessário;
- eventos;
- evidência;
- artefatos;
- resultado;
- hashes e referências sanitizadas.

## O que não atravessa por padrão

- memória pessoal completa;
- histórico íntimo desnecessário;
- tokens em texto;
- cookies;
- segredo bruto;
- acesso ilimitado ao PC;
- autoridade final.

# 11. SEGURANÇA SEM BUROCRACIA

O Pivete não deve ser obrigado a confirmar vinte vezes.

## Autorização por missão

```text
PIVETE AUTORIZA O ESCOPO UMA VEZ
→ sistema trabalha dentro do contrato
→ só interrompe por bloqueio real
```

## Proteções invisíveis no motor

- workspace isolado;
- backup automático;
- diff;
- teste;
- snapshot;
- segredo fora de logs;
- limite por projeto;
- publicação explícita;
- rollback pronto;
- proteção contra force-push;
- proteção contra exclusão fora do escopo;
- proteção contra produção errada;
- registro automático.

## Quando interromper o Pivete

Somente quando houver:

- escolha de produto;
- risco real de perda;
- gasto novo;
- publicação;
- conflito de intenção;
- ausência de credencial indispensável;
- alvo não identificável;
- resultado visual que exige gosto pessoal.

Todo o restante deve ser pesquisado e resolvido pelos agentes.

# 13. BUILDER — COMPONENTES OBRIGATÓRIOS

## 13.1 Projetos

- criar a partir de template;
- importar repositório;
- importar módulo existente;
- clonar projeto;
- arquivar;
- restaurar;
- mostrar origem e proprietário.

## 13.2 Workspace isolado

- um workspace por projeto/execução;
- branch ou snapshot identificável;
- dependências isoladas;
- limite de recursos;
- limpeza controlada;
- persistência dos artefatos aprovados.

## 13.3 Chat de construção

- conversa com contexto do projeto;
- escolha automática de modelo;
- ordens em linguagem comum;
- plano breve;
- execução;
- progresso visível;
- explicação do resultado.

## 13.4 Preview ao vivo

- URL própria por workspace;
- HMR quando aplicável;
- estado carregando/pronto/falhou;
- captura automática;
- comparação visual;
- console coletado;
- erro traduzido.

A tecnologia final — WebContainer, container remoto, iframe ou combinação — só será decidida depois do inventário real.

## 13.5 Loop automático

```text
ALTERAÇÃO
→ BUILD
→ PREVIEW
→ ERRO?
   → classificar
   → corrigir
   → testar novamente
→ RESULTADO VISUAL
```

Abortar quando houver estagnação real, não por limite arbitrário.

## 13.6 Publicação

O botão PUBLICAR deve:

1. congelar o candidato;
2. registrar referência;
3. executar testes definidos;
4. mostrar impacto;
5. criar commit/PR ou promoção configurada;
6. publicar;
7. verificar saúde;
8. guardar rollback;
9. informar resultado em linguagem simples.

## 13.7 Voltar

- listar versões;
- mostrar miniatura/diferença;
- restaurar candidato anterior;
- verificar saúde;
- preservar histórico.
